# 剩余非风格静态诊断复核与下一批建议

日期：2026-11-16。源码基准：`9d6ee31`。

后续任务已拆分：[静态诊断修复](../plans/static_diagnostics_fixes_2026-11-16.md)负责 RIS4、唯一标签及精度/接口问题；
本报告中的 CSF P1 由[描述符读取迁移](../plans/csf_descriptor_migration_2026-11-16.md)承接，包括旧入口仍在使用时的最小保护。
下文保留发现时的证据和优先级，不表示这些问题已修复。新对话应重新核对当前源码及退役目标。

本报告接续[首次静态分析](fortls_fortitude_analysis_2026-11-16.md)及
[第一批修复验证](priority_input_safety_fixes_2026-11-16.md)。本轮只分析、制作临时探针及记录建议，
没有修改生产源码、正式测试或构建配置，没有提交或推送。

## 1. 结论与优先级

下一批优先处理 CSF 输入的失败语义，其次处理 RIS4 缓存探测和唯一 LS 标签读取。
精度声明、接口约束和可移植性分开处理，不能把全部 Correctness 诊断当作运行缺陷。

| 优先级 | 项目 | 核定结果 | 建议范围 |
| --- | --- | --- | --- |
| P1 | 共享 CSF 头/列表读取及 transition 副本 | 已复现错误输入被接受、错误退出码为 0；有未成功读入的字符串参与解析 | `lib9290/lodcsh.f90`、`lodcsl.f90` 与三份 `rtransition*/lodcslm.f90`，连同 MPI 调用端的错误传播 |
| P2 | RIS4 角向缓存探测 | 空/截断缓存导致 Fortran 运行时错误，未按“不完整缓存”处理 | `ris4/angdata.f90` 的 OPEN、BACKSPACE、尾记录 READ、REWIND 与缓存可用性契约 |
| P2 | JJ2LSJ 唯一标签读取 | 确认未检查头记录；后续正 IOSTAT 错误也未拒绝，局部读语句探针已复现 | `jj2lsj_code.f90::uniquelsj`，区分 EOF、转换错误、完整记录及空输入 |
| P2，独立数值改动 | 活跃表达式中的默认实常量 | 20 条常量先按默认实数舍入；SCF 人工临界值会改变分支，未证明实际计算失准 | 按算法用途明确 kind，先覆盖四份 SCF、`rwfnestimate`，再核定 QED/矩阵判据及输出阈值 |
| P3 | 显式类型与接口约束 | 48 份接口存在加入 IMPLICIT NONE 前必须处理的声明顺序；不是当前构建失败 | 先调整接口声明依赖顺序，再按程序族补 IMPLICIT NONE、回调接口及 INTENT |
| P3 | 指针初始状态、日志重定向等 | 有防御性改进空间；未定位当前正常调用链的指针访问缺陷 | 单独维护，不与前三项异常输入修复混合 |

P1 表示应优先修复的实际行为问题；P2 表示范围较窄的实际缺陷或已证实的精度风险；
P3 表示接口、防御性和可维护性工作，不代表已经发生了错误计算。

## 2. 覆盖与验证方法

- Fortitude 仍为 0.10.1；按当前源码重新扫描 `C,PORT,OB,E`，包含 preview，使用 Fortran 2018、132 列，
  明确关闭自动修复。覆盖 `src/`、`test/` 的 1,908 份第一方 Fortran 文本，得到 20,576 条诊断。
  该口径包含额外 portability/obsolescent 规则，不能直接与旧默认规则的 35,361 条比较。
- C181 从旧基准的 107 条降为 13 条，C161 为 0，C022 从 8 条降为 4 条。
  逐项复核了这 13 条 C181，以及小集合的初始化、指针、分支、分配、不可达代码和名称遮蔽诊断。
- fortls 既有 57 条诊断涉及的 14 份文件与首次分析的 SHA-256 全部一致；沿用其解析对照证据，
  没有将旧结果说成一次新的全仓库 fortls 扫描。
- 用 GNU Fortran 15 和已有 Check 库编译五个 CSF 驱动、一个 RIS4 驱动，运行 35 个输入场景。
  直接调用现有过程，未改写过程实现。MPI 目录中的 `lodcslm` 在本轮以独立单进程驱动调用，
  **没有进行新的多 rank 故障回归，也没有复现 MPI 挂起**。
- 对 C001/C002 涉及、且有当前编译命令的 966 份文件，执行 1,107 个带 `-fimplicit-none` 的语法探查。
  所有模块输出放在独立临时目录，未替换正式构建模块。
- 源码扫描的 1,908 份输入以哈希记录；本轮未运行生产 SCF、性能或物理收敛计算。

较大的 USE ONLY、INTENT、数组接口、可变模块状态等集合仍需按调用关系逐项审查。
本报告不声称已证明所有剩余诊断安全，也不把低优先级等同于已完成治理。

## 3. 已确认的输入问题

### 3.1 P1：CSF 读取失败与非法记录没有可靠地向调用方报告

关键位置：

- [lodcsh.f90](../../src/lib/lib9290/lodcsh.f90) 第 96–102 行：READ 后不查 `ios` 就调用 `prsrcn`，
  随后也不查 `ierr`，直接计算 `electron_count`。
- [lodcsl.f90](../../src/lib/lib9290/lodcsl.f90) 第 176–188 行：READ 后先访问 `record`，
  第 470 行起把第一次读取失败归入“至少一个 CSF”的后备分支。
- [rtransition/lodcslm.f90](../../src/appl/rtransition/lodcslm.f90) 第 167–175 行及 MPI/phase 副本：
  同样在检查状态之前使用字符串；未区分合法结束与其他输入错误。
- `lodcsl` 第 554 行起、三份 `lodcslm` 第 543 行起的拒绝路径最终使用无非零状态的 `STOP`。

以 `data/test.c` 的首个完整 CSF 为控制，输入来自其前 5、6、7、8 行及一个非法占据数副本：

| 输入 | 过程 | 实际观察 |
| --- | --- | --- |
| 完整首个 CSF | 五个读取器 | 正常返回；核电子 10 加价电子 18，共 28 电子 |
| 有 12 个 peel 轨道但没有 CSF 记录 | `lodcsh` | 观察到返回 10 电子，也观察到 `prsrcn` 的 `cnum` 索引越界；未读入字符串造成行为不稳定 |
| 同上 | `lodcsl` 与三份 `lodcslm` | 返回“1 个 CSF、22 电子”，即错误地使用了头部的 peel 轨道数；没有实际读入 CSF |
| 第一条占据数含 `x` | `lodcsh` | 打印“could not be decoded”后仍正常返回 10 电子 |
| 缺子壳层行、缺耦合行、非法占据数 | `lodcsl` 与三份 `lodcslm` | 打印错误并 STOP，但进程退出码为 0，未返回驱动的成功标志 |
| 仅闭核、peel 行为空且没有 CSF 列表 | `lodcsl` 与三份 `lodcslm` | 后备分支返回 1 个闭核 CSF、10 电子；应保留这个合法边界契约 |

不能简单将“没有显式 CSF 行”一律拒绝：当前代码有闭核后备语义。
但有 peel 轨道却缺失首条记录时，不能继续使用未定义记录，或把轨道数当作价电子数。
头部驱动只读取头与首个占据行，因此它在“缺后续耦合行”场景返回本身不属于失败。

建议同时处理 READ 状态、`prsrcn` 返回值、合法闭核后备分支、错误退出码，
不要只在第一个 READ 后补一个 IF 就宣称完成。
[rmcdhf_mpi/setcslmpi.f90](../../src/appl/rmcdhf_mpi/setcslmpi.f90) 第 73 行在 rank 0 调用 `lodcsh`，
之后广播轨道数和电子数；修复时应让错误传播到 MPI 入口统一处理，保持公共 `lib9290` 无 MPI 依赖。

下一批回归至少覆盖完整首个 CSF、合法闭核、有 peel 的空列表、非法占据数、缺两类必需记录、
块分隔符及正常 EOF，并验证串行非零失败与单 rank 错误时整组 MPI 退出。

### 3.2 P2：RIS4 的不完整缓存不能安全降级

[angdata.f90](../../src/appl/ris4/angdata.f90) 第 53–61 行打开已有 `.IOB/.ITB`，
BACKSPACE 的 `istat` 被忽略，随后 READ 没有错误处理。

实际驱动结果：缺失文件返回 `avail=.false.`；完整 `-1` 结束记录返回 `.true.`；
普通未完成尾记录返回 `.false.`；但空文件、只有两个字节的截断文件均以运行时 EOF 错误退出，代码 2。
这与过程已有的“不完整缓存返回不可用”路径不一致，是确定的鲁棒性缺陷。

建议把缓存缺失、不完整、无法读取分开诊断，并明确何时重新计算、何时报错；
失败时正确关闭 unit，避免仅在 READ 上增加 STOP。
MPI 调用端 [ris_cal_mpi.f90](../../src/appl/ris4/ris_cal_mpi.f90) 第 178 行起只在 root 探测缓存，
随后广播可用性；需补 root 失败的多 rank 验证。本轮只复现了串行运行时失败。

### 3.3 P2：唯一 LS 标签读取不拒绝正 IOSTAT

[jj2lsj_code.f90](../../src/appl/jj2lsj/jj2lsj_code.f90) 的 `uniquelsj`：

- 第 3390 行读取首行后不检查状态，直接写出 `record`。
- 第 3415 行读混合系数，仅在 `ios==-1` 时按 EOF 处理；转换错误时仍使用 `str`、`mix`、`comp` 等。
- 在后续最大分量选择中，还应明确空分量列表的拒绝条件，防止未设置的选择下标被使用。

从源码逐字提取第 3415–3416 行 READ，输入非法数值字段后得到 `IOSTAT=5010`，
`ios==-1` 为假，证明当前 EOF 分支没有涵盖转换失败。
这只是原读语句的小样本，不是完整 `uniquelsj` 故障复现；本轮没有运行其巨大工作区或改小生产容量。
该过程在 `unique==1` 时由控制器调用，读取本次生成的 unit 57，因此优先级低于公共 CSF 入口。

建议使用命名 EOF 状态、完整检查每条记录，并为零级数/零分量、格式错误、截断输入补回归。
现有唯一标签分配算法与输出格式应作为正常路径对照。

## 4. 精度诊断：保留 ABI，区分常量与表达式

剩余四条 C022 都不属于上一批 EPS 问题：

- 三份 `getrmp/getrmpmpi` 的默认 `real :: cnum(3)` 仅有声明，没有使用；改成 double 不会改善现有数值行为。
- [linear_algebra_interfaces.f90](../../src/lib/libmod/linear_algebra_interfaces.f90) 第 17 行的 `slamch`
  是单精度 LAPACK 返回接口，必须保持匹配；不能批量改成 double。

C021 的 97 条中，77 个字面量本身能精确表示，20 个不能：

| 表达式用途 | 位置/副本数 | 建议 |
| --- | --- | --- |
| SCF 收敛条件 `0.001*accy` | `rmcdhf{,_mem}/scf.f90:227`、两份 MPI `scfmpi.f90:250` | 优先统一 double；补阈值两侧和正常迭代输出对照 |
| 初始轨道节点阈值 `0.05`、求解器 `0.1e00/0.2e00` | `rwfnestimate/genrwf.f90:59`、`solvh.f90:63,234,236` | 明确计算 kind，按求解器行为验证 |
| QED 区间 `0.0219` | 两份 `rci/qed.f90` | 核对边界网格选择，避免将“编译通过”当作数值等价 |
| 矩阵求逆默认判据 `1.0e-8` | 两份 `rbiotransform/bndinv.f90:97` | 检查判据附近矩阵和正常矩阵 |
| JJ2LSJ 提示、权重筛选和归一提示 | 5 条 | 区分仅显示用数值与参与选择的数值 |
| transition 能差一致性提示 | 三份 `printaLS.f90:51` | 核对提示边界，不能据此推断跃迁计算已有物理错误 |

GNU 15 实测：默认 `0.001` 提升为 double 后为 `1.00000004749745131E-3`，
显式 double 为 `1.00000000000000002E-3`。取两者之间的人工临界值时，原 SCF 表达式为真、
double 表达式为假。它证明存在分支边界差异，**不证明正常原子计算的收敛结论已经改变**。

77 个精确字面量也不自动证明整个表达式以 double 运算。
例如两份 `systemfreemem` 用整数 `summem * 1.0 / 1048576.0` 先做默认实数运算，
再赋值给 double；当前调用点用于打印内存信息，宜作为较低优先级的数值一致性维护。

## 6. IMPLICIT NONE 不能机械批量插入

本轮编译探查以当前 Check 命令为基础，额外增加 `-fimplicit-none -fsyntax-only`，
不改 CMake 的实际选项。结果是 1,056 个上下文通过，51 个失败，涉及 48 个不同接口文件。

失败均有“维度变量先使用、后声明”的根因。例如
[interp_I.f90](../../src/lib/lib9290/interp_I.f90) 第 10–12 行先出现 `dimension(narr)`，后声明整数 `narr`。
没有 IMPLICIT NONE 时，现有接口通过原编译配置；禁用隐式类型后，GNU 15 严格模式拒绝这个顺序，
并产生数组形参没有类型的连带报错。

核对所有失败上下文的维度名，均能找到对应整数声明；仅在临时探查中允许 GNU 声明顺序扩展后，
这 51 个上下文全部通过。该对照用来解释根因，**不是建议放宽生产编译标准**。
未发现这组失败来自实际漏声明的拼写错误；也不能由此证明所有接口与过程实现完全一致。

建议先把维度/长度参数放在依赖它们的声明之前，再加过程作用域的 IMPLICIT NONE。
回调 `cord/breid` 当前有五个整数参数，`rkco_gg` 已有带 `procedure(cord_callback)` 的接口；
清理调用端 EXTERNAL 时须同时核定类型、kind、rank 和 INTENT，不能只按工具自动建议替换。

14 份没有当前编译命令的候选未进入该探查；清单保存在本地结果中。
其他 C003/C061/C071/C072/C121/C131/C202 等大集合仍属于按模块逐步核定的接口或状态管理工作，
不是本轮已确认的缺陷总数。
