# rangular MPI/OpenMP：x86 本机复现与原因诊断

日期：2026-11-11。源码基准：`c47f4d42b1f60bd77eb04dd3a243f545d124f481`。
本次完成性能诊断与 MCP 输出对照，没有修改生产计算代码，没有进行 SCF/RCI 或物理精度验证。
CSFG 不在本次范围内。

**结论：x86 上仍然复现 OpenMP 8 线程约为 MPI 8 进程两倍的耗时。首要问题是当前两条路径的并行范围不同，其次是 OpenMP 逐列批次的同步、局部负载尾部和串行结果提交。不能把差距归结为 M4 的 ARM 架构，也不能据此认为 OpenMP 技术本身必然比 MPI 慢。**

## 1. 实验目标与边界

此前 [M4 对照报告](rangular_mpi_openmp_benchmark_2026-11-11.md) 的原始输入、运行器和输出只在 Mac 上，当前无法独立复核该报告的原始数据。
本次使用工作区已有的另一套完整 CSF 输入，在 x86 上检验“OpenMP 是否仍然落后”，再缩到一个完整对称性 block 进行阶段诊断。
因此不能通过两份报告的速度比直接比较 ARM 和 x86。

实验预期不是预设 OpenMP 应当更快：若差距仍在，并且生成的 MCP 数值相同，就继续区分并行范围、同步开销、单线程开销和运行参数的影响。

| 条件 | 本次配置 |
| --- | --- |
| CPU | 运行环境报告 AMD Ryzen 7 7800X3D；可见 8 CPU、每核 1 线程、1 socket、1 NUMA 节点；可用 CPU 集合 0–7 |
| 工具链 | GNU Fortran 15.3.0、Open MPI 5.0.11 |
| 构建 | 同一批 `build-ordinary-mpi-production` Release 产物，复制后固定身份；`f2018-release`，CSFG 关闭 |
| 实际编译选项 | 应用及角系数库 `-O2`，OpenMP 对象另加 `-fopenmp`；没有引入旧标准兼容选项 |
| 输入 | 文本 CSF，两条路径相同；28 电子、41 轨道、23,459 CSFs |
| block 大小 | 1,506 / 3,933 / 5,768 / 6,276 / 5,976 |
| 相互作用 | full interaction；stdin 为 `y` |
| 并行环境 | 8 线程或 8 MPI ranks；数学库固定 1 线程；`OMP_DYNAMIC=false`；MPI 显式 `--bind-to none` |
| 文件系统 | 运行目录在本机 `/tmp`，其文件系统为 tmpfs；不代表服务器磁盘或 NFS 性能 |
| 计时范围 | 子进程启动到退出，MPI 包含 launcher/startup/finalization；输入复制和输出比较在计时之外 |

完整输入 SHA-256：
`7e2bf6eeec279db065bc85401c72b73f93644ffe3da3896ee3f59e417d9e63ab`。
完整三角区域共有 63,065,280 个候选 CSF 对，输出有 38,461,197 项系数贡献。

编译选项以生成的 `flags.make` 和链接命令为准。
`CMakeCache.txt` 中通用的 `CMAKE_Fortran_FLAGS_RELEASE=-O3` 缓存值不是本构建最终使用的选项；
[FortranProfiles.cmake](../../cmake/FortranProfiles.cmake) 在配置作用域将其设为 `-O2`。

所有计时运行按顺序执行，没有同时编译或进行耗 CPU 的数值比较。
早期 `block4-8-baseline` 两轮与完整输出比较发生重叠，其时间已经标记为不可用并排除；其数值比较结果仍然有效。
后续用 `block4-clean` 和 `phases-*` 重做无重叠测量。

## 2. 完整输入结果：差距在 x86 上成立

| 运行 | OpenMP 8 线程 / 秒 | MPI 8 进程 / 秒 |
| --- | ---: | ---: |
| 第一轮，OMP → MPI | 27.0607 | 13.7511 |
| 第二轮，MPI → OMP | 27.3089 | 12.9582 |
| 第三轮，OMP → MPI | 25.5485 | 13.4852 |
| 中位数 | **27.0607** | **13.4852** |

中位数之比为 **2.0067**。这不是只有 Mac 才出现的现象。

第一轮以 `mcp_compare` 在 `atol=rtol=0` 下比较全部 38,461,197 项系数贡献，差异为 0。
后两轮分别与各自后端第一轮的完整 MCP 文件集合做 SHA-256 对照，文件集合和内容全部相同。
MPI 输出为 rank 分片；比较器按 CSF 对及系数内容进行语义对照，没有把分片文件的字节布局当成串行布局。
计时也没有包含把 MPI 分片额外合并成单套串行 MCP 的步骤；现有 MPI 下游消费的是分片。

取总耗时恰为中位数的第一轮 OpenMP，阶段如下。并行批次时间是生成阶段的子项，不能再次相加：

| 阶段 | 秒 |
| --- | ---: |
| 文本头部及 CSF 加载 | 0.3749 |
| 角系数生成与缓冲，包含并行批次 | 17.6132 |
| 其中：并行批次 | 14.3017 |
| 生成阶段中批次之外的工作 | 3.3115 |
| 稀疏结构与输出 | 0.9914 |
| 排序与输出 | 8.0462 |
| 程序内总计 | 27.0418 |

排序与输出已经占约 30%。批次以外的全部时间为约 **12.74 秒，占 47%**。
若只加速 `parallel_batch_compute`、其它路径完全不变，那么即使该子项降到零，这一轮仍需约 12.74 秒。
反过来，即使把排序时间全部消掉，其余部分仍需约 19 秒，高于当前 MPI 的整程时间。
所以只优化角动量内核、只调整输入加载，或只改排序中的某一处，均不足以消除所有差距。

## 3. 主要原因：MPI 并行了更完整的流程

代码路径对比如下：

| OpenMP 当前路径 | MPI 当前路径 |
| --- | --- |
| 当前 JA 列的 JB 范围切成小任务 | JA 列按 rank 循环分配，`JA=1+myid,NCF,nprocs` |
| worker 生成原始角系数，保存到 tile | rank 生成角系数并直接过滤、记录 |
| 每批结束等待所有 worker | 本 block 的生成循环中没有逐列集合屏障 |
| 主线程逐对读回、过滤、编号、写入全局缓冲 | rank 自己完成局部编号、临时文件和稀疏结构 |
| 主线程排序、写出完整 MCP | 各 rank 并行排序、写出各自 MCP 分片 |

对应实现为 [rangular_parallel.f90](../../src/appl/rangular/openmp/rangular_parallel.f90) 的
`prepare_batch` / `load_parallel_pair`，以及
[mcp_gg.f90](../../src/appl/rangular/mcp_gg.f90) 和
[mcpmpi_gg.f90](../../src/appl/rangular_mpi/mcpmpi_gg.f90)。
MPI 在输入、block 切换和结束时仍有协调，不能把它描述为完全没有同步。

为验证并行范围，提取原输入第 4 个完整 block：6,276 CSFs、19,697,226 候选对、11,881,459 项最终贡献。
零容差比较通过后，在独立构建目录为 MPI 加入 rank 阶段计时，为 OpenMP 加入 tile/批次边界计时。
探针只替换应用层对象，继续链接原 Release 的角系数内核和库；没有在每个 CSF 对内调用时钟。
两种探针版输出均与各自未插桩基准字节一致。

| 单 block 阶段 | OpenMP 8 线程探针 / 秒 | MPI 各 rank 范围 / 秒 |
| --- | ---: | ---: |
| CSF 加载，MPI 另含广播及临时文件设置 | 0.0898 | 0.1008–0.1009 |
| 生成及结果存储，MPI 含临时文件写入 | 4.6355 | 2.3872–2.4908 |
| 其中：OMP 并行批次 | 3.6924 | 不适用 |
| 稀疏结构及输出 | 0.2927 | 0.0405–0.1370 |
| 排序及输出 | **2.4450** | **0.4154–0.4334** |
| 进程外完整墙钟 | 7.4753 | 4.8125，整个 MPI 作业 |

MPI rank 的各阶段会交叠，各行最大值可能来自不同 rank，不能把这些最大值简单相加作为作业墙钟。
MPI 阶段时钟覆盖 `startmpi2` 返回后至 `stopmpi2` 调用前，各 rank 共 2.95–3.07 秒；
外部计时还包含启动和结束。`stopmpi2` 最终执行 STOP，因此不能把它之后未执行的诊断标记算成有效测量。
外部墙钟与阶段总计的差值也不能全归为通信。

未插桩的相邻控制运行是 OMP 6.9947 秒、MPI 5.0391 秒。
OMP 探针版慢约 7%，MPI 探针版没有出现正向增时；由于调度波动和插桩扰动，线程子项用于识别机制，不作为无误差的精确成本分账。
其它无重叠单 block 默认 OMP 运行在约 7.0–8.8 秒范围；不能只挑最快一轮宣传优化。

MPI 每 rank 只处理约 148 万项系数，而 OMP 主线程处理完整的约 1,188 万项。
两条路径都使用 heapsort，但 MPI 对较小的分片分别排序，OMP 对完整列表串行排序。
排序的工作量分布和内存工作集也随之不同；缓存收益具有合理性，但本次没有硬件计数器证据，不能单独给它分配百分比。

## 4. 第二个原因：总体均衡掩盖了每批的等待

8 线程时，控制器最多创建 32 个 tile；任务不跨 JA 列。
`rows_per_tile` 由当前剩余行数和 tile 数计算，`--pair-chunk` 只是上限。
本 block 默认上限 256，实际最大 tile 只有 197 对，因此每列仍要经过一次 `omp parallel` 区域，总计 **6,276 次批次**。
把上限改成 1024 并不会把这些列合成更大的任务，也不会减少这里的批次数。
这里的重复是并行区域进入/退出及同步，不等于操作系统每次重新创建全部线程。

探针实测：

| OMP worker 统计 | 每线程累计值 |
| --- | ---: |
| tile 计算，含结果保存 | 2.163–2.242 秒，平均 2.194 秒 |
| 显式记录的批次屏障等待 | 1.219–1.290 秒，平均 1.261 秒 |
| 每批最慢线程的 tile 时间，再跨批累加 | 3.411 秒 |
| 整个并行批次区域累计墙钟 | 3.692 秒 |

各 worker 的总计算时间最大值只比均值高约 2.2%，但每批必须等待本批最慢线程。
跨批累积的最长 tile 路径为 3.411 秒，明显高于 worker 平均累计计算 2.194 秒。
因此长期总工作量分配接近均衡，仍会出现大量局部尾部等待。
测得的等待包含局部任务成本差异和系统调度影响；本次没有把两者完全分离，也没有将整个批次时间误称为纯同步开销。

相比之下，MPI 在这个样例中的每 rank 最终系数数目最大值仅比均值高 0.72%，生成阶段最大时间比均值高 2.49%。
原有循环列分配在该输入上已相当均衡，因此“动态分配一定优于 MPI 的静态分配”没有得到支持。

## 5. 第三个原因：结果要经过额外搬运和串行处理

OMP 的 `compute_tile` 把原始 LABEL/COEFF 从线程私有内核缓冲复制到 tile；
`load_parallel_pair` 又把它们复制回主线程缓冲，然后原 MCP 逻辑才做阈值/F0 过滤、标签整理、位置编号和最终缓冲写入。
候选对即使没有系数，也要建立 tile 元数据并由主线程逐对读取。

该 block 探针记录了 11,885,020 项原始二电子系数，每项保存 5 个整数标签和 1 个双精度数，共 28 字节。
两次显式复制合计搬运约 **666 MB 的有效载荷**，尚不含读写两端、逐对元数据、最终数组扩容及排序访存。
这说明额外数据处理确实存在；不能把这些字节数直接换算成实测 DRAM 流量或认定内存带宽已饱和。

在未插桩单 block 控制运行中，生成阶段减去并行批次为 0.933 秒；完整输入的代表轮中为 3.311 秒。
该差额还包含主线程过滤、缓冲扩容、结构临时记录、批次准备等，**不是单独测出的 memcpy 时间**。
本次默认 64 MiB 结果缓冲未发生 tile spill，因此不足以用“结果溢出磁盘”解释当前慢速。
普通 MCP 的全局排序缓冲也是另一组内存，`--result-memory-mib` 并非整个进程内存上限。

## 6. 已检查但不能作为主因的解释

**单线程 TLS/编译退化。** 同一 block、同一批 Release、相同输出：普通串行 `rangular` 21.7044 秒，
OMP 1 线程 20.5956 秒。这里只是单次控制，不能宣称 OMP 1 线程稳定更快；
但没有复现 M4 报告中 OMP 1 线程明显更慢的现象。Mac 的 TLS 实现、大小核调度等仍需 Mac 本机证据，不能反推为本机根因。

**等待策略、绑定和 chunk。** 同一 block 的单项变化试验：

| 配置，按实际运行次序 | 秒 |
| --- | ---: |
| 默认，前控制 | 7.7728 |
| `OMP_WAIT_POLICY=PASSIVE` | 7.3813 |
| `OMP_WAIT_POLICY=ACTIVE` | 7.5507 |
| `OMP_PROC_BIND=close`、`OMP_PLACES=cores` | 7.8139 |
| `--pair-chunk 32` | 7.5272 |
| `--pair-chunk 1024` | 7.5104 |
| 默认，后控制 | 7.4957 |

这些是单轮机制探针，不足以排名最优参数；输出均与控制字节相同。
没有哪项将耗时降到同阶段 MPI 的约 5 秒水平。

另做一组含 CPU 时间的等待策略对照：PASSIVE 墙钟 7.4541 秒、累计 CPU 20.8226 CPU 秒；
默认墙钟 8.4907 秒、累计 CPU 40.9458 CPU 秒，输出字节相同。
这组数据支持等待策略可以显著减少忙等消耗，但墙钟改善幅度还需重复测量，不能据此承诺固定收益。
GNU libgomp 的 [等待策略说明](https://gcc.gnu.org/onlinedocs/libgomp/OMP_005fWAIT_005fPOLICY.html)
与 [spin count 说明](https://gcc.gnu.org/onlinedocs/libgomp/GOMP_005fSPINCOUNT.html) 区分了主动忙等和被动等待。
所以 CPU 利用率高不必然表示有用计算多；低利用率也不能单凭观察就认定是 I/O。

**单机 MPI 的通信代价。** 这条 MPI 热循环没有逐对通信，通信主要位于输入和阶段边界。
Open MPI 支持 [同节点共享内存通信](https://docs.open-mpi.org/en/v5.0.x/tuning-apps/networking/shared-memory.html)，
因此“MPI 必然经过网络，所以换 OpenMP 必然更快”不成立。
本次没有采集实际 BTL/CMA 选择，不能宣称测得了某种传输机制的收益。

**输入和兼容编译选项。** 两条路径使用同一文本输入；完整 OMP 输入加载只占约 0.375 秒。
描述符适配器有加载收益，但不能修复当前十余秒的整程差距。两种并行程序均使用生产 `-O2`，
没有为这次诊断恢复 `-fno-automatic`、参数不匹配放行等选项。

## 7. 后续改造优先级

1. **扩大任务覆盖范围，并减少逐列屏障。** 将完整列或跨列片段交给 worker，在整个 block 内保持同一线程团队，
   让空闲 worker 能领取后续列；继续限制缓冲容量。单纯增大目前的 chunk 上限达不到这一目标。
2. **让 worker 完成更多结果处理。** 在 worker 内过滤并生成紧凑贡献，设计确定性的列计数/前缀位置编号，
   减少原始结果双重复制和主线程逐对重放。需要明确最终 MCP 的顺序、位置号和重复贡献契约。
3. **并行化排序及输出阶段。** 可按系数通道或分片安排独立任务，再完成确定性输出。
   现有 [sortmem.f90](../../src/appl/rangular/sortmem.f90) 使用固定文件 unit 29 和共享数组接口，
   不能直接在外层添加 OpenMP directive；先显式传入独立数据和文件上下文。
4. **再优化运行参数和内核。** PASSIVE 可作为减少忙等的候选，但不是解决串行尾部的方法。
   TLS、缓存未命中、false sharing、NUMA 等要有新的针对性证据后再处理。

这些是待实施的改造方向，本次没有实施或声称验证其加速效果。
当前生产上继续使用已验证更快的 MPI 路径是合理选择；OpenMP 首版实现了并行生成和本次样例的输出一致性，
其整程性能仍受设计范围限制。是否值得替代 MPI，应在下一版相同输入、相同物理核数、相同输出契约下再判断。

下一轮应优先在实际 x86 服务器使用这套完整输入及同样的阶段计时复核，再考察服务器特有的 NUMA、绑核和磁盘路径。
目前没有 10 万 CSFs、大型多 socket 或其它 GRASP 程序的性能结论，也不把 rangular 的诊断外推到 rmcdhf。

## 8. 本地证据与复查

诊断脚本、固定输入/二进制身份、两种隔离探针源码及精简日志保存在本地忽略目录
`build-rangular-diagnosis-20261111/`，不提交计算数据和机器路径：

- `identity.json`：源码、输入、二进制 SHA-256 和硬件信息。
- `analysis-summary.json`：完整三轮统计、阶段统计、线程计时、限制说明。
- `full8-baseline-1-comparison.json`、`block4-clean-1-comparison.json`：零容差数值对照。
- `single-and-full-probes.json`：串行/单线程控制及完整输入重复、输出哈希验证状态。
- `phase-probes.json`、`runtime-probes.json`、`wait-cpu-probes.json`：机制对照。
- `evidence/`：各有效运行的 stdout/stderr、执行元数据、阶段 CSV 和 rank/worker CSV 副本。
- `build_instrumentation.py`、`instrumented/`：隔离探针；未改动 `src/` 中生产实现。

完整 MCP 输出保留在诊断脚本记录的临时运行目录；精简证据已复制到上述本地目录。
若需要复查同机的可执行差分循环，在仓库根目录运行以下 fish 命令。运行前必须确保没有另一项计时或数值比较同时执行：

```fish
set diagnosis_label (date +%Y%m%d-%H%M%S)
../graspkit-tools/.venv/bin/python build-rangular-diagnosis-20261111/diagnose.py \
    --case block4 --workers 8 --repeat 1 --label review-$diagnosis_label
```

该本地诊断入口包含输出语义比较。退出码 1 表示“输出比较成功，但 OMP 墙钟仍高于 MPI”的性能现象被复现；
退出码 0 表示该次 OMP 不再更慢。程序异常或比较差异也会导致失败，须同时检查 JSON 的 `status`、
`equivalence` 和 `symptom_reproduced`，不能只依据退出码判断程序错误。
正式性能门槛仍应使用多轮统计，单次差分循环只用于定位现象。
