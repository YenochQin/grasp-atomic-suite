## 1. Scope

`1.0.1-dev.1` focused on the hot path of `RHFS_MPI -> HFSGG_MPI`, especially the large number of one-particle matrix-element evaluations and the recoupling precheck chain behind `ONEPARTICLEJJ2/RECOP2`.

This branch contains three kinds of work:

- retained optimizations that are now in `main`
- temporary profiling/instrumentation used to locate the hotspot
- optimization attempts that were later reverted because they did not help

An earlier phase-1 writeup is already in [RHFS_MPI_hfsgg_optimization.md](RHFS_MPI_hfsgg_optimization.md). This document is the branch-level summary for the full `1.0.1-dev.1` line.

## 2. Optimizations And Current Retention Status

### 2.1 `HFSGG_MPI` outer-loop prefilter and zero screening

File:

- [src/appl/rhfs90/hfsgg_mpi.f90](../../src/appl/rhfs90/hfsgg_mpi.f90)

Main retained changes:

- Before calling `ONEPARTICLEJJ`, the code now performs cheap outer-loop rejection:
  - `ITRIG(...)` triangular-condition screening
  - parity screening
  - occupation-difference scan between `IC` and `IR`
- The old idea of relying on deeper routine rejection was replaced by rejecting impossible pairs earlier in `HFSGG_MPI`.
- `ELEMFAC`, `GJFAC`, and `DGJFAC` are precomputed once and then reused in the hot accumulation loop.
- When a pair differs in exactly two occupations, the code now checks whether the corresponding matrix-element factors are already zero before calling the expensive one-particle path.
- During shell accumulation, zero matrix-element factors are skipped directly instead of multiplying through the full expression every time.

Why this matters:

- It cuts down the number of expensive `ONEPARTICLEJJ` calls.
- It removes work items that would later collapse to zero anyway.
- It shortens the cost of the remaining shell-to-element accumulation path.

Related commits:

- `cf197a2` `Pre-filter HFSGG MPI one-particle calls`
- `a2ec419` `Optimize HFSGG MPI zero-element screening`

### 2.2 `HFSGG_MPI` correctness fix that protects the optimized path

File:

- [src/appl/rhfs90/hfsgg_mpi.f90](../../src/appl/rhfs90/hfsgg_mpi.f90)

Retained change:

- `delta g_J` precompute order was fixed so that `DGJFAC` is formed after the needed angular/radial pieces are prepared.

Why this matters:

- This is not a speed optimization by itself.
- It is a correctness fix for the optimized precompute path and prevents using partially prepared data.

Related commit:

- `abf4e07` `Fix HFSGG MPI delta g_J precompute order`

### 2.3 `RECOP2` fast precheck experiment for `IRE = 0` (not retained)

File:

- [src/lib/librang90/recop2.f90](../../src/lib/librang90/recop2.f90)

Historical change and current outcome:

- `f414fb6` added a dedicated early path for `IRE = 0`.
- `505d7f4` subsequently removed that branch while adding diagnostic instrumentation.
- The current `RECOP2` still executes the common chain and coefficient-product updates;
  it does not contain this independent fast path. The fast paths in `DIAGA3/DIAGA4` remain.

Why this matters:

- The hotspot analysis showed that `RECOP2(..., IRE=0)` was executed very frequently.
- The proposed boolean-style path sought to remove coefficient arithmetic, but it cannot
  be counted among the final retained optimizations in this checkout.

Related commits:

- `f414fb6` `Optimize RECOP2 precheck path`
- `505d7f4` `Instrument RECOP2 precheck failure stages` (also removes the fast path)

### 2.4 `DIAGA3` fast path for `IRE = 0`

File:

- [src/lib/librang90/diaga3.f90](../../src/lib/librang90/diaga3.f90)

Main retained changes:

- For `IRE = 0`, `DIAGA3` now uses only `IXJTIK(...)` feasibility checks.
- It returns `REC = 1` once the chain is confirmed admissible.
- It avoids the heavier `SIXJ` work that is only needed when the actual coefficient must be formed.

Why this matters:

- Profiling showed that this path dominated the `RECOP2` precheck time.
- This change keeps the cheap logical gate and skips the expensive coefficient build.

Related commit:

- `d2da0dd` `Optimize DIAGA3 precheck path`

### 2.5 `DIAGA4` fast path for `IRE = 0`

File:

- [src/lib/librang90/diaga4.f90](../../src/lib/librang90/diaga4.f90)

Main retained changes:

- For `IRE = 0`, `DIAGA4` now replaces the `NINE(...)` call with a sequence of `ITTK(...)` checks.
- Only when the real coefficient is needed does the code call the full `NINE(...)` path.

Why this matters:

- This removes repeated heavy recoupling work from the precheck-only stage.
- It complements the `RECOP2` and `DIAGA3` fast paths and shortens the full precheck chain.

Related commit:

- `77620c2` `Optimize DIAGA4 precheck path`

## 5. What The Branch Ultimately Improved

In final retained form, `1.0.1-dev.1` improved the code in two layers:

1. In `HFSGG_MPI`, it reduces the number of expensive one-particle evaluations and skips zero-contribution work earlier.
2. In `DIAGA3/DIAGA4`, it converts the high-frequency `IRE = 0` path into a cheap feasibility check instead of a full coefficient-construction path. The independent `RECOP2` branch was not retained.

In short:

- fewer useless calls enter `ONEPARTICLEJJ`
- fewer zero terms survive into shell accumulation
- less recoupling algebra is executed during precheck-only calls

## 6. Observed Performance Notes

From the validated runs recorded during this branch:

- after the kept `DIAGA3/DIAGA4` work and after reverting the `DIAGA1` attempt, the stable good result was around:
  - `HFSGG_MPI kernel wall time`: about `798.5 - 798.9 s`
  - `HFSGG_MPI reduce wall time`: about `18.4 - 19.5 s`
  - total wall time: about `818 - 821 s`
- the `DIAGA1` optimization attempt regressed in the observed run to roughly:
  - `HFSGG_MPI kernel wall time`: `821.929 s`
  - `HFSGG_MPI reduce wall time`: `37.832 s`

This is why the branch kept the `DIAGA3/DIAGA4` path changes but explicitly rolled back the `DIAGA1` experiment.
